Reference · tool

shyzctl

A small command-line tool that keeps this documentation honest. It derives the API contract from the Express source, records examples from the running service, answers questions about the error catalogue, and fails the build when a page drifts from the code.

Why a CLI and not a wiki

Documentation written next to code decays the moment the code moves. The usual answer is discipline. The answer here is a tool with a narrow job and an exit code: an endpoint that exists in a page but not in the contract is an error, not a review comment. Everything the site claims can be re-derived in one command.

python tools/shyzctl.py contract build    # parse server/index.js -> contract JSON
python tools/shyzctl.py verify            # does every page still match?
python tools/capture.py                   # re-record the 39 examples

Top-level help

usage: shyzctl [-h] [--version] <command> ...

Documentation contract CLI for the CoorColor / SHYZ API reference site.

positional arguments:
  <command>
    contract   derive or re-check the API contract
    endpoints  list endpoints from the contract
    show       print one endpoint with its documented errors
    explain    look up an error catalogue entry
    verify     check the published site against the contract
    docs       build the static site
    exitcodes  print the exit-code table

options:
  -h, --help   show this help message and exit
  --version    show program's version number and exit

Exit codes: 0=OK, 1=FINDINGS, 2=USAGE, 3=MISSING_INPUT, 4=DRIFT, 5=INTERNAL

Exit codes

Every command exits with one of six codes. The table is generated from the tool's own constant, so it cannot disagree with the implementation — and argparse returns 2 for a malformed command line before the tool runs at all.

CodeNameMeaning
0OKEvery check passed, or the requested data was printed.
1FINDINGSOne or more documentation defects were found. Details on stdout.
2USAGEThe command line was wrong. argparse also exits 2 for unknown flags.
3MISSING_INPUTA required file (source, contract or catalogue) does not exist.
4DRIFTThe committed contract no longer matches the Express source.
5INTERNALUnexpected crash. This is always a bug in shyzctl, never in the docs.

A pipeline can therefore distinguish the cases that need different responses: a broken cross-reference (1) is a documentation bug, a stale contract (4) is a code change that landed without regenerating, and 3 means the checkout is incomplete rather than wrong.

Inspect one route before writing about it. The source range, the auth model and every error string with the line that raises it come from the contract, not from the page:

PUT /api/admin/orders/:id/assign
  source          server/index.js:1026-1058
  auth            none
  status codes    [200, 400, 404]
  errors
    400  请选择工程师  (line 1030)
    404  订单不存在  (line 1036)
    404  工程师不存在  (line 1039)

Ask the catalogue a question without opening the site:

E-ASG-MASK  An unknown order masks an unknown engineer
  endpoint     PUT /api/admin/orders/:id/assign
  http         404
  message      订单不存在
  symptom      The engineer id in the form is out of date, but the error blames the order.
  cause        Checks run body, then order (:1036), then engineer (:1039). Two different failures share one status code and one envelope, so the second is unreachable while the first fails.
  next step    Fix the order id first, then re-run the call to surface the engineer error. When the endpoint gains error codes, give the two 404s different ones so the UI can point at the right field.
  verify       capture-fail passes a live engineer against an unknown order and receives 订单不存在 rather than 工程师不存在.
  doc          api/put-admin-orders-assign.html#errors

And run the whole check. This is the command a CI job calls; it is also the command to run after editing any page by hand:

OK: contract, catalogue, links and support tags all resolve.
What verify actually inspects

Five things: every data-endpoint a page claims exists in the contract; every data-status and data-message a page quotes is produced by that route; every catalogue link resolves to a file and an anchor; every internal link and anchor on every page resolves; and every support tag used in the review points at a page that actually carries it.

Requirements

  • Python 3.9 or later, standard library only. No virtualenv, no dependencies, nothing to install for the documentation build.
  • The recording script (tools/capture.py) needs the service running and, for the payment pages, a sandbox copy — see the source repository's README.
  • The CLI never talks to the network. The only network traffic in this workflow is capture.py against localhost.
