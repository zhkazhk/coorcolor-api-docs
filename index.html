Writing sample

Documentation for an API I built, and the checks that keep it true

CoorColor is a printer-service back office — 63 HTTP endpoints behind a mini program and an admin console. This site is the documentation for it: 9 reference pages, a CLI reference, a 17-entry error catalogue, a style guide, a review rubric, and a model-versus-model review that applies the rubric to two drafts of the same page.

How it is verified

Nothing on this site is typed from memory. Three files decide what is true, and every page is generated from them:

contracts/shyz-api-contract.json
Parsed from the Express source: 63 endpoints, their status codes, their exact error strings and the line of code that raises each one.
contracts/captures.json
39 request/response pairs recorded against the running service with tools/capture.py. Every example on this site is one of these pairs.
errors/catalog.json
The catalogue as data. The page you read is rendered from it, and shyzctl explain answers from it.
python tools/shyzctl.py contract check     # has the source drifted?
python tools/shyzctl.py verify             # does the site still match?
python tools/capture.py                    # re-record every example

The verify run is the point. It fails the build when a page documents an endpoint the contract does not have, quotes an error string the source does not raise, cites a capture id that was never recorded, or links to an anchor that does not exist. The exit codes are documented, so a pipeline can tell a broken link from a stale contract.

Scope, stated plainly

  • Eight of the 63 endpoints are documented in depth — the eight most likely to be integrated: sign-in, SMS code, product list, order creation, order detail, assignment, payment creation, payment callback. The other 55 appear in the inventory with their status codes, generated from the contract.
  • The two payment pages were recorded against a sandbox copy of the service whose outbound calls to the payment platform are stubbed and whose merchant key is a dummy. Signing is the real implementation; no live merchant account was touched.
  • Credentials were redacted line-in-place before publication. tools/redact_snapshot.py does the redaction and refuses to write a file if any credential-shaped string survives.
  • This is a sample of the writing and the verification, not a product manual. The product is an internal system; the Chinese strings are real because they are wire values.

What the sample is meant to show

  • I can turn a codebase I own into documentation without inventing anything: the contract and the captures are the source, and the prose reads the facts out of them.
  • I separate describing what the code does from judging what it should do. The error catalogue has a severity, names defects (a payment amount taken from the client, a callback that can never verify), and does not pretend the system is finished.
  • I can review documentation, not just write it: the rubric is written down before the review, the two drafts were produced independently, and the verdict carries a one-line reason with tags that point at the pages I checked.
Known limitation

The two review drafts come from the same model in two separate sessions with no shared context. That is enough to show a repeatable review procedure and to catch real defects, but it is not evidence about two different vendors. A cross-vendor comparison would need the same brief sent to a second provider — the rubric and the tag format would not change.
