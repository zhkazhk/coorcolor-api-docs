Error catalogue

17 entries, each written from a recorded request, not from reading the code alone. Every row resolves to a page anchor, and every capture_fail / capture_fix id exists in contracts/captures.json, so the catalogue can be re-verified after a code change.

How to use it

Start from the symptom you can see, not from the message you cannot explain. Each entry names the request that produced it, the line of code behind it, and the smallest change that fixes it. Query the same data from a terminal with shyzctl explain E-ASG-MASK.

E-AUTH-BEARER — Authenticated call answers 请先登录 even though the client sent a token

Endpoint
GET /api/user/addresses
HTTP
401
message
请先登录
Severity
blocker
Source
server/index.js:312

Symptom. Every authenticated request returns 401 请先登录. The token in local storage is valid and the account exists.

Cause. The handlers require the header to start with Bearer (server/index.js:312), but the shipped client sends the bare token: 'Authorization': wx.getStorageSync('token') in utils/api.js:18. The prefix is never added anywhere.

Next step. Send Authorization: Bearer <token>. One-line client fix: 'Authorization': 'Bearer ' + (wx.getStorageSync('token') || ''). Decide the convention once and document it in the client wrapper, not in each page.

How to verify. The two captured pairs differ only in the header: capture-fail returns 401 请先登录, capture-fix returns 200 with an empty address list.

Documented at. api/authentication.html#bearer-prefix

E-AUTH-FORGED — A badly signed token is reported as an expired session

Endpoint
GET /api/user/addresses
HTTP
401
message
登录已过期
Severity
medium
Source
server/index.js:317

Symptom. A token that was never valid (wrong signature, tampered payload) produces 登录已过期, the same message as a genuinely expired one.

Cause. The handler wraps jwt.verify in a blanket try/catch (server/index.js:317-326) and maps every error, including JsonWebTokenError, to the expiry message. The global error middleware that distinguishes the two (server/index.js:1397-1403) is never reached because the handler swallows the error first.

Next step. Branch on the error: TokenExpiredError → 登录已过期, anything else → 无效的登录凭证. The client can then decide between refresh and re-login instead of guessing.

How to verify. capture-fail uses a well-formed JWT with a replaced signature and receives 登录已过期, which proves the collapse.

Documented at. api/authentication.html#verification

medium
Source
server/index.js:63

Symptom. Wrong credentials return one of two different texts: 用户不存在 or 密码错误.

Cause. server/index.js:63 and :68 answer separately for a missing account and a wrong password. Combined with no rate limiting anywhere in the service, the pair turns sign-in into a username oracle.

E-AUTH-ADMIN-TOKEN — An administrator token passes every user route and reads as an empty account

Endpoint
GET /api/user/addresses
HTTP
200
message
—
Severity
high
Source
server/index.js:214

Symptom. With a valid admin token, user endpoints return HTTP 200 and empty payloads. The address list is [], never the addresses that exist.

Cause. Only one login exists and it mints {id, username} (server/index.js:65). User handlers read decoded.phone (server/index.js:321), which is undefined for an admin token, so the filter matches nothing. jwt.verify succeeds, so nothing is rejected either.

Next step. Add a user-scoped login that signs {phone} and keep the two token audiences apart, for example with a typ claim and a check per route family. Treat the empty 200 as a data-loss symptom, not as a normal empty state.

How to verify. capture-fix sends the admin token with the correct prefix and still returns {"code":0,"data":[]}.

Documented at. api/authentication.html#token-shapes

HTTP

medium
Source

Symptom. abcdefghijk is accepted and a verification code is issued for it.

Cause. The only check is phone.length !== 11 (server/index.js:264). The validatePhone helper with the real 1[3-9]\d{9} pattern already exists in the same file (server/index.js:34) and is not used here.

Severity
blocker
Source

Symptom. The API answers 验证码已发送, the user's phone stays silent, and the six digits appear only in the server log.

Cause. There is no SMS provider integration. server/index.js:274 does console.log with the code; the in-memory store at server/index.js:202 is the only destination.

Next step. Until a provider is wired, do not describe this as sent. In the integrator guide, state plainly that the code is delivered out of band, and add the provider call plus failure handling before any release that depends on it.

E-ORD-ID-COLLISION — Two orders created in the same millisecond share an id

Endpoint
POST /api/orders
HTTP
200
message
—
Severity
high
Source
server/index.js:87

Symptom. Two order records with the same id; later reads return whichever one the lookup finds first.

Cause. id: Date.now().toString() (server/index.js:87) is the only identifier strategy for orders, addresses, ratings and reviews. Under concurrent submission, or a client retry loop, duplicate keys are reachable.

Next step. Key on a monotonic counter, a UUID, or the order number with its random suffix widened. order_no (CK + date + four random digits) is 10 000 values per day, which is better than a millisecond but still not unique.

How to verify. Send two creations in parallel with curl --parallel; compare data.id. The capture set cannot show this, because it is a race, so the check is the reproduction above.

Documented at. api/post-orders.html#identifiers

E-ORD-NOTFOUND — A stale order id answers 404 with the same envelope as a validation error

Endpoint
GET /api/orders/:id
HTTP
404
message
订单不存在
Severity
low
Source
server/index.js:190

Symptom. Opening an order from a bookmark returns 404 订单不存在. The client cannot tell this from a malformed request, because both carry code: -1.

Cause. Only the HTTP status separates the cases (server/index.js:190). The body has no error taxonomy, so any client that reads code treats every failure the same.

Next step. Treat 404 as 'remove it from the list' rather than 'show an error', and refresh the list on it. See E-ENVELOPE if you need a machine-readable reason.

How to verify. capture-fail uses a well-formed but unknown id and receives 404; capture-fix shows the same request with a live id.

E-ASG-MASK — An unknown order masks an unknown engineer

Endpoint
PUT /api/admin/orders/:id/assign
HTTP
404
message
订单不存在
Severity
medium
Source
server/index.js:1036

Symptom. The engineer id in the form is out of date, but the error blames the order.

Cause. Checks run body, then order (:1036), then engineer (:1039). Two different failures share one status code and one envelope, so the second is unreachable while the first fails.

Next step. Fix the order id first, then re-run the call to surface the engineer error. When the endpoint gains error codes, give the two 404s different ones so the UI can point at the right field.

How to verify. capture-fail passes a live engineer against an unknown order and receives 订单不存在 rather than 工程师不存在.

E-STATE-COMPLETE — Completing an order that is not in progress fails without saying what state it is in

Endpoint
PUT /api/admin/orders/:id/complete
HTTP
400
message
只能完成服务中的订单
Severity
medium
Source
server/index.js:1090

Symptom. Completion is refused on an order the operator believes is in progress. The message names the required state but not the current one.

Cause. The guard compares against processing only (server/index.js:1090) and answers with a fixed string. The handler does not echo the current status, so the operator has to reload the detail view to find out.

Next step. Reload the order, confirm the status, and drive it to processing (confirm, then start, or assign) before completing. Prefer showing the current status in the UI rather than relying on the message.

How to verify. capture-fail completes a pending order and is refused; capture-fix completes the same order after assignment, when it is processing.

E-STATE-START — Starting a pending order is refused because confirm was skipped

Endpoint
PUT /api/admin/orders/:id/start
HTTP
400
message
只能开始已确认的订单
Severity
medium
Source
server/index.js:1065

Symptom. Start is refused on a freshly created order. The operator sees no reason in the message for the missing step.

Cause. start requires confirmed (server/index.js:1065), while assign jumps straight to processing without confirming. Two routes reach processing, and only one of them needs the confirm step, which makes the required sequence inconsistent.

Next step. Choose one path and document it. Today: assign (which forces processing) or confirm then start. Do not mix them in one workflow.

How to verify. capture-fail starts a pending order; confirm-ok then start-ok show the two-step path succeeding.

—
Severity
blocker
Source
server/index.js:1657

Symptom. A request for twelve rentals at ¥899 each, submitted with totalAmount: 0.01, is accepted and a payment for one fen is prepared.

Cause. totalAmount is copied from the body into the order and into total_fee (server/index.js:1624, :1657). The product records are never consulted, so nothing ties the charge to the catalogue price.

Next step. Recompute the amount server-side from items[].productId and the product price, and reject a body whose totalAmount disagrees. Do not deploy a payment path that trusts the client for money.

E-PAY-CALLBACK-XML — The payment callback rejects every notification, including correctly signed ones

Endpoint
POST /api/wxpay/callback
HTTP
200
message
签名错误
Severity
blocker
Source
server/index.js:1688

Symptom. Every callback from the payment platform is answered return_code=FAIL, return_msg=签名错误, so an order never becomes paid through the callback.

Cause. bodyParser.json() is registered globally (server/index.js:14) and there is no XML parser. req.body is {} for application/xml, so parseXML (:1688) yields no parameters, sign is undefined, and verifySign (:1694) cannot succeed. The failure is silent because HTTP is still 200.

Next step. Register a text or raw parser for application/xml before the route, and confirm with a captured round trip. Until then, reconcile payments with GET /api/wxpay/order/:orderNo, which does flip the status.

How to verify. capture-fail carries a signature computed exactly as the platform requires (sorted pairs, &key=, MD5 upper-case) and is still refused, which isolates the cause to body parsing rather than to the signing code.

Documented at. api/post-wxpay-callback.html#signature

E-ENVELOPE — There is no error taxonomy: code is always 0 or -1

Endpoint
cross-cutting
HTTP
400
message
—
Severity
high
Source
server/index.js:1394

Symptom. Every failure looks identical to a program: {"code":-1,"message":"…"}. Clients branch on the HTTP status, or worse, on the Chinese string.

Cause. The success path uses code: 0, every failure uses code: -1 (62 distinct message strings, one code). No error code, no field name, no request id — so a client cannot react to 库存不足 differently from 订单不存在 without string matching.

Next step. Introduce stable codes such as ORDER_NOT_FOUND, keep message for humans, and add field where validation failed. Version the change by adding fields, never by changing existing strings.

How to verify. shyzctl endpoints --json lists the status codes per endpoint; shyzctl show POST /api/orders shows the single code value used for eight different validation failures.

Documented at. api/authentication.html#envelope
