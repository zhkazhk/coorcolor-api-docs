<2 id="a-assign">Assign an order to an engineer

This endpoint assigns an engineer to an existing order and moves that order into the processing state in one call. Call it from an admin or dispatcher screen once a person has picked an engineer, passing the order id that POST /api/orders returned in data.id. The response is the full updated order, so you can re-render the order detail view from it without a follow-up read.

<3 id="a-request">Request
NameInTypeRequiredDescription
idpathstringYesId of the order to assign, as returned by POST /api/orders in data.id.
engineer_idbodystringYesId of the engineer to assign, for example engineer001. Send a non-empty string; the body needs no other field.

Send the body as application/json:

{"engineer_id":"engineer001"}

A complete request:

curl -X PUT "<BASE_URL>/api/admin/orders/<ORDER_ID>/assign" -H "Content-Type: application/json" -d '{"engineer_id":"engineer001"}'
<3 id="a-response">Response

Success returns HTTP 200 with the full updated order object:

{"code":0,"data":{"id":"<ORDER_ID>","order_no":"<ORDER_NO>","service_type":"repair","brand":"HP","model":"","problem_desc":"Drum unit replacement","urgency":"normal","photos":[],"position":null,"appointment_date":"2026-11-04","appointment_time":"09:30","contact_name":"Wang Fang","contact_phone":"13900000003","service_address":"Floor 6, 1000 Century Avenue, Pudong, Shanghai","remark":"","status":"processing","created_at":"<ISO-8601>","updated_at":"<ISO-8601>","engineer_id":"engineer001","engineer_name":"张工程师","engineer_phone":"13800138001","timeline":[{"status":"processing","time":"<ISO-8601>","operator":"管理员","remark":"分配给工程师：张工程师"}]}}

Compared with the order before the call, engineer_id, engineer_name and engineer_phone now hold the assigned engineer's values, status is processing, updated_at is refreshed, and timeline has one extra entry recording the assignment with operator 管理员 and remark 分配给工程师：张工程师; every other field is unchanged.

<3 id="a-errors">Errors

Every failure uses the same envelope, with the readable text in message:

{"code":-1,"message":"请选择工程师"}

There are no machine-readable error codes, so match on the message string rather than on the number.

HTTPmessageWhen it happensWhat to do
400请选择工程师engineer_id is missing, empty or otherwise falsy. This is checked before the order is looked up.Validate the engineer selection in the UI and resend with a non-empty id.
404订单不存在No order matches :id.Recheck the id; it must come from data.id of the order creation call.
404工程师不存在No engineer matches engineer_id. Checked only after the order resolves.Reload the engineer list and send an id that exists.
<3 id="a-behaviour">Behaviour worth knowing
  • The handler writes four things: it copies engineer_id, engineer_name and engineer_phone from the engineer record, sets status to processing, appends a timeline entry {"status":"processing","time":"<ISO-8601>","operator":"管理员","remark":"分配给工程师：<engineer name>"}, and refreshes updated_at.
  • Checks run in a fixed order: body, then order, then engineer. A bad engineer_id therefore surfaces as 请选择工程师 even when the order does not exist, and an unknown order returns 订单不存在, which masks an unknown engineer.
  • The handler performs no token check, and nothing on this route enforces admin rights. Treat the endpoint as unauthenticated and keep your own authorization in front of it; do not rely on it to protect order data.
  • There is no state guard on status. Because status is overwritten unconditionally, assigning an already completed order silently reopens it as processing, and its earlier timeline entries stay in place.
  • Repeated calls are not deduplicated: a second assign for the same order rewrites the engineer fields, keeps status at processing, and appends another timeline entry.
