Standards

Review rubric

Four dimensions, scored 1 to 5, plus a decision rule that is written down before the drafts are read — so the verdict is repeatable and the reasoning is auditable rather than a matter of taste.

The four dimensions

DimensionWeightWhat it asks
Accuracy0.4Is every claim true of the system? Field names, status codes, message strings, ordering, side effects.
Completeness0.2Are all the required sections present, and is anything a caller needs missing?
Actionability0.2Can a developer act on it without asking a question — examples runnable, “what to do” concrete?
Tone0.2Sentence case, second person, no marketing, consistent terms, no filler.

The decision rule

Scores alone invite arithmetic to settle an argument. The rule used here puts accuracy first and is applied in this order:

  1. Count accuracy defects: each distinct claim that is untrue of the system, or internally inconsistent with the same document. Score accuracy from that count.
  2. If one draft has strictly fewer accuracy defects and is not worse on completeness, actionability or tone, it is preferred.
  3. If the defect counts are equal, the result is a tie — regardless of the weighted score. A pleasant document that is wrong is still wrong.
  4. Report weighted scores as context. They never overturn the accuracy test.
Why not choose on the weighted score

A weighted average lets strengths in tone buy off a factual error. In an API reference a wrong field name costs a developer an afternoon; elegant prose saves them ten seconds. The weights still matter — they decide how much a defect costs once the accuracy question is settled — but they do not decide the winner.

How to run the review

  1. Fix the brief in writing before drafting: the facts, the required sections, the tag allowlist, the length. Both drafts get the same brief and no rubric.
  2. Draft independently. No shared context, no sight of the other draft, the same stylesheet applied afterwards so formatting cannot influence the read.
  3. Read both against the source, not against each other. Keep a defect list with the line number or capture id that proves each one.
  4. Score, apply the decision rule, then write one line of reasoning and the support tags. The tags are the audit trail: they point at the pages that were checked.

Support tags

Every verdict carries tags of the form [API-ref], [error-catalog] or [exit-code], and each tag resolves to a page anchor on this site. A tag is a claim that a human verified that page against the source during this review — not a label for the topic.
