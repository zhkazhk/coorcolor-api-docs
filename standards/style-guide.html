Standards

Style guide

One page, because a style guide nobody reads is worse than none. These are the rules this site is written to, and the review rubric scores drafts against them.

Who is reading

A developer integrating against an API they did not build, under time pressure, usually with one screen of code open and one tab of documentation. They are looking for a field name, a status code, or an example they can paste. Write for the skim: the first sentence of a section has to be true and useful on its own.

Voice

  • Second person or imperative. “Send the id you received…” not “the id will be sent…”. The reader is the actor.
  • Present tense for behaviour, imperative for instructions. “The handler answers 404” describes; “Check the id before retrying” instructs. Do not mix them in one sentence.
  • No adjectives that cannot be verified. Seamless, powerful, robust, simple, easy: cut. If it is easy, the example shows it.
  • Say the consequence, not the feeling. “A retried call appends a second timeline entry” beats “retries are not handled gracefully”.
  • Do not soften defects. “This route performs no authorization check” is the sentence. Not “authorization is handled elsewhere”.

Chinese strings

The wire values are Chinese. Reproduce them exactly, inside code, and do not translate them in the error tables — a reader matches what they see in the console. Translate only around them: “answers 404 订单不存在 for an unknown id”.

Where a string is a poor identifier (it says nothing a program can branch on), say so once in the page that a reader will land on, and link to the catalogue entry that proposes the fix. Do not repeat the complaint on all nine pages.

Code samples

  • Run what you publish. Every example on this site is a recorded request/response pair. If it was not executed, it is not shown.
  • Placeholders in angle brackets and escaped: <ORDER_ID>. Volatile values (ids, timestamps, tokens, signatures) are never published as literals.
  • Elide with an ellipsis only at the end of a payload, and never remove a field a reader needs to see.
  • One sample per shape. A second sample is worth its space only when it shows a different shape — a failure, or a different state.

Cross-references

  • Link to the anchor, not the page: authentication.html#bearer-prefix.
  • Every internal link and anchor is checked by shyzctl verify, so a renamed heading fails the build instead of rotting.
  • Cite the source as file:line-line in a span, not in a sentence: the reader who does not care should be able to skip it without losing the sentence.
  • A claim that there is a defect must link to a catalogue entry with evidence. “This is unsafe” without a capture or a line number is an opinion.

When to break these rules

Two exceptions, both used on this site. A validation message that is a joined list is quoted once as a whole and then taken apart in a table, because reproducing it inline would be unreadable. A payment page whose examples come from a sandbox says so in a callout before the first sample, because provenance outranks brevity.

The test is not “does this look like the guide”. It is “would a reader be misled”. If breaking a rule prevents a wrong conclusion, break it and say why in the review.
