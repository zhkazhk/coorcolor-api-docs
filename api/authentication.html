Reference · guide

Authentication and errors

Two cross-cutting rules decide most integration bugs: what a caller must put in the Authorization header, and what a failure actually looks like. Both are simpler than they look and both are easy to get wrong, because the shipped client gets the first one wrong already.

The response envelope

Every JSON response, success or failure, has one shape:

{"code": 0, "data": <payload>}          // success, HTTP 200
{"code": -1, "message": "<Chinese text>"}  // failure, HTTP 4xx or 5xx

code is only ever 0 or -1. It is not an error code; it is a boolean with JSON syntax. The contract records 62 distinct message strings sharing that single -1, so a client that branches on code cannot distinguish a missing order from insufficient stock.

Consequence

Branch on the HTTP status, and treat message as display text. Do not compare the string to decide control flow: it is Chinese prose that any localisation change will break. See E-ENVELOPE for the proposed taxonomy.

Bearer tokens

User and address routes require the header in one specific form:

Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...

The handlers test `startsWith('Bearer ')` before doing anything else (server/index.js:312). A bare token is not a token to this service: it produces 401 请先登录, which reads like “you are not signed in” even though the caller is holding a valid credential.

The shipped mini program sends the bare token

utils/api.js:18 does 'Authorization': wx.getStorageSync('token') with no prefix, so every authenticated call from the client fails with 请先登录. The fix is one line — see E-AUTH-BEARER.

The global error middleware does distinguish JsonWebTokenError from TokenExpiredError (server/index.js:1397-1403), but it never runs for these routes because the handler catches the error first. A client cannot tell “refresh me” from “you were never authenticated”.

Two token shapes, one login

There is one sign-in endpoint and it issues an administrator token. Its payload is {id, username}. User routes read decoded.phone, which an administrator token does not contain.

The result is a silent empty account rather than a rejection: the verify step succeeds, the filter matches no rows, and the caller receives HTTP 200 with an empty list.

Read an empty list as a symptom

An authenticated user route that returns [] may mean the token in hand is an administrator token. E-AUTH-ADMIN-TOKEN records the capture and the suggested fix (a user-scoped login plus a token audience claim).

Routes without authorization

Most /api/admin/* routes perform no token check at all. The contract's auth column records this per route, and it is worth stating without a hedge: an unauthenticated caller can read the customer list, change order state, approve reviews, and delete products.

The documentation does not paper over this. Each affected page says so in its own Behaviour section, so an integrator reading one page cannot miss it, and the inventory marks the routes. Fixing it is an application change, not a documentation one; until it ships, treat the network boundary as the only access control.
