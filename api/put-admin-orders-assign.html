PUT/api/admin/orders/:id/assign

Assign an engineer to an order

Attaches an engineer to an order and moves it to processing in one call, without asking what state the order was in.

Source
server/index.js:1026-1056
Auth required
No — the handler performs no token check
Effect on status
Forced to processing, unguarded
Idempotent
No — every call appends a timeline entry

Request

NameInTypeRequiredDescription
idpathstringYesOrder id from POST /api/orders, data.id.
engineer_idbodystringYesAn existing engineer id such as engineer001. Any falsy value is rejected before the order is read.

Response

The full updated order. The selected engineer's id, name and phone are copied onto it, status becomes processing, and a timeline entry records the operator and the engineer's name:

FieldNotes
statusAlways processing after this call, whatever it was before.
engineer_name, engineer_phoneCopied from the engineer record so a detail view needs no second lookup.
timeline[]New last entry: {"status":"processing", "operator":"管理员", "remark":"分配给工程师：<engineer name>"}.
updated_atRefreshed.

Errors

HTTPmessageWhen it happensWhat to do
HTTP 400请选择工程师engineer_id is missing, empty or otherwise falsy. Checked before the order is looked up.Require a selection in the UI and block the call until one is set.
HTTP 404订单不存在No order matches id. Raised after the body check and before the engineer lookup.Re-read the order list; the id must come from data.id of the creation call.
HTTP 404工程师不存在No engineer matches engineer_id. Unreachable while the order id is also wrong.Reload the engineer list and send an id that exists.

Checks run body, then order, then engineer, and each failure replaces the knowledge of the next one. A dispatcher with two stale ids is told about the order only. See E-ASG-MASK.

Where this sits in the state machine

Orders move through five statuses. Two routes reach processing, and they do not agree about what must happen first:

FromCallToGuard
pendingPUT /api/admin/orders/:id/confirmconfirmedRequires pending: 400 只能确认待处理订单
confirmedPUT /api/admin/orders/:id/startprocessingRequires confirmed: 400 只能开始已确认的订单
processingPUT /api/admin/orders/:id/completecompletedRequires processing: 400 只能完成服务中的订单
anyPUT /api/admin/orders/:id/assignprocessingNo guard — a completed order is silently reopened
pending / confirmed / processingPUT /api/admin/orders/:id/cancelcanceledRefuses completed and canceled
The assign route bypasses the confirm and start steps entirely, so the same order can reach processing by two different histories.

Because status is overwritten rather than transitioned, assigning an order that is already completed returns it to processing and leaves the completion entry in the timeline. Nothing in the response flags that a finished job was reopened.

Two rules, one status

Confirm-then-start is guarded at every step; assign skips both. If a UI exposes only one of them, the other is reachable by API and produces a state the UI does not model. Documented, not fixed: the fix is a guard on status in the assign handler.

Behaviour worth knowing

  • No authorization. Nothing on this route checks a token, so any caller who can reach the port can reassign work. Several admin routes share this property; the contract's auth column lists them all.
  • Not idempotent. A retried call rewrites the engineer fields and appends a second timeline entry, so the log records two assignments for one decision. Guard retries on the client.
  • The engineer is not validated as available. An engineer record with status: inactive or one who is already on another job can be assigned; order_count on the engineer record is never incremented here.
  • The timeline is the audit trail. It is the only record of who changed what, it is append-only, and its operator value is a fixed Chinese string rather than the caller's identity — so it cannot attribute an action to a person.
