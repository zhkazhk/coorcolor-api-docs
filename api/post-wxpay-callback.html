POST/api/wxpay/callback

Payment callback

The notification endpoint the payment platform calls after a payment. It answers in XML, verifies an MD5 signature, and flips the order to paid. In this build it rejects every callback, including correctly signed ones.

Source
server/index.js:1680-1718
Auth required
Signature, not a token
Transport
XML in, XML out, HTTP 200 in every case
Status in this build
Cannot verify — see Signature below

Request

The platform posts an XML document with CDATA-wrapped fields. The ones the handler uses are result_code, out_trade_no, transaction_id and sign; anything else is ignored.

Response

The answer is XML, and the HTTP status is always 200. Success and failure differ only inside the body, which is what the platform reads:

<xml><return_code><![CDATA[SUCCESS]]></return_code><return_msg><![CDATA[OK]]></return_msg></xml>
<xml><return_code><![CDATA[FAIL]]></return_code><return_msg><![CDATA[签名错误]]></return_msg></xml>

There are four failure texts: 签名错误, 系统错误, 处理失败, and the platform's own err_code_des when result_code is not SUCCESS (falling back to 支付失败).

The signature can never match

The handler parses the body, then verifies an MD5 signature over the sorted parameters plus the merchant key. A body is never parsed:

app.use(bodyParser.json());            // server/index.js:14 — JSON only
...
const params = await wxpayUtils.parseXML(xmlData);   // :1688, receives {}

No XML parser is registered, so for Content-Type: application/xml the body parser leaves req.body as an empty object. parseXML therefore finds no fields, sign is undefined, and verifySign cannot return true.

Consequence and workaround

Orders are never marked paid by the callback, so a paid rental stays pending until something queries it. The workaround that does work is GET /api/wxpay/order/:orderNo, which asks the platform directly and flips the status on trade_state: SUCCESS. The fix is to register a text parser for application/xml before this route. E-PAY-CALLBACK-XML.

Behaviour worth knowing

  • Failure is invisible to monitoring: every response is HTTP 200, so an uptime check cannot tell a working callback from a broken one. Watch the body, not the status.
  • A callback that does verify would update the order by out_trade_no, and would be safely repeatable — the handler assigns status = 'paid' rather than incrementing anything.
  • The route has no anti-replay protection of its own; it relies on the platform's signature, which is precisely the part that is not working here.
  • The callback configures notify_url in wxpay-config.js, which points at the reverse-proxied host — it is not the localhost base URL the rest of this reference uses.
