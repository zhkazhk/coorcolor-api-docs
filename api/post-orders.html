POST/api/orders

Create a service order

Books an on-site visit: service type, machine, problem, appointment, contact and address, validated by one middleware that reports every missing field at once.

Response

Only the two identifiers come back. Everything else the client just sent is not echoed, so a confirmation screen has to re-read the order.

FieldNotes
data.idOrder id, a millisecond timestamp as a string. Used in every order URL.

Errors

Validation is one middleware, validateOrderData. It collects every failing rule, then answers a single 400 whose message is the reasons joined by a full-width semicolon, in the order the rules are checked:

OrderRuleReason text (verbatim)
1serviceType non-empty服务类型不能为空
2brand non-empty品牌不能为空
3problemDesc non-empty问题描述不能为空
4appointmentDate non-empty预约日期不能为空
5appointmentTime non-empty预约时间不能为空
6contactName ≥ 2 chars请输入正确的联系人姓名
7contactPhone matches the mobile pattern请输入正确的手机号
8serviceAddress ≥ 5 chars请输入详细的服务地址
Reasons appear in this order, joined with ；. A client that wants to highlight one input has to match on the string.
The response has no field name

Nothing in the body says which input failed, so the console has to parse the joined prose or repeat the same eight rules client-side. See E-ORD-VALIDATION.

Identifiers

id is Date.now().toString() (server/index.js:87). Two orders submitted within the same millisecond receive the same id, and the second one shadows the first on every lookup. The order number is not a substitute: it is CK + date + four random digits, which is a 10 000-value space per day.

This is a documentation fact worth repeating on the page rather than leaving in a ticket, because it changes how a client should behave: never treat id as globally unique, and avoid parallel submissions from one session. E-ORD-ID-COLLISION has the reproduction.

Behaviour worth knowing

  • No authorization check. An unauthenticated caller can create an order for any phone number and address they like, and the record will look like a real booking.
  • The middleware validates contactPhone properly, while the SMS routes next door accept any eleven characters — the two endpoints disagree about what a phone number is.
  • Dates and times are only checked for presence. 2020-01-01 and 99:99 are accepted, so past-dated bookings are a client-side problem by design.
  • The created order starts as pending with an empty timeline. See the state machine for what can happen next.
Evidence
