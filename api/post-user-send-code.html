POST/api/user/send-code

Send a verification code

Issues a six-digit code for a phone number and keeps it in memory for five minutes. No SMS is sent: the code is written to the server log.

Validation

The check is phone.length !== 11 (server/index.js:264). A number with eleven non-digits passes:

A short number is rejected, which is the only failure this route has:

A stricter validator already exists

validatePhone with /^1[3-9]\d{9}$/ is defined in the same file (server/index.js:34) and used by order validation, but not here. See E-SMS-LEN.

Delivery

There is no SMS provider integration. The code is generated, stored in a module-level object, and printed:

const code = String(Math.floor(100000 + Math.random() * 900000));
verificationCodes[phone] = { code, expiresAt: Date.now() + 5 * 60 * 1000 };
console.log(`发送验证码 ${code} 到 ${phone}`);

Three consequences follow directly, and all three are visible in the source rather than inferred:

  • The user never receives anything. Any flow that depends on the code arriving on a phone cannot complete in production.
  • The store is a plain object with no eviction, so it grows for the life of the process; a restart drops every pending code.
  • Requesting a code for the same number twice overwrites the previous one, silently invalidating a code the user may already be holding.

Then what

Verification is a separate call, POST /api/user/bind-phone, which accepts phone and a six-digit code. Its failures are 400 with one of four messages: 请输入正确的手机号, 请输入6位验证码, 请先获取验证码, 验证码已过期, 验证码错误 — a wrong code looks like this:

Because no code is delivered, a working end-to-end sign-in currently requires reading the code out of the server log. Say so in release notes rather than describing the flow as complete.
