Reference · orders

GET/api/orders/:id

Read an order

Returns one order, enriched with the assigned engineer's name, phone and last reported position. The engineer fields are added at read time and are not stored on the order.

Read-time enrichment is not persistence

The handler writes engineer_name, engineer_phone and engineer_position onto the in-memory order object (server/index.js:195-197). They are not saved. A list endpoint returns the same order without them, so do not assume the fields exist on every order you receive.

Errors

HTTPmessageWhen it happensWhat to do
HTTP 404订单不存在No order matches id.Remove the order from the list or refresh it; a stale id means the record is gone, not that the request was malformed.

The 404 carries the same code: -1 as a validation failure, so the HTTP status is the only signal that distinguishes “gone” from “wrong”.

Behaviour worth knowing

  • No authorization check: knowing an id is sufficient to read a customer's name, phone and address.
  • The response is assembled per request from two collections, so an order whose engineer_id no longer resolves keeps the id and returns engineer_name: "" rather than failing.
  • Volatile fields scramble comparisons: engineer_position.updated_at changes whenever the engineer reports, and nothing in the payload version-stamps the order for caching.
